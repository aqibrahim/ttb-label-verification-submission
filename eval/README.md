# Evaluation Harness

This measures how the extraction + comparison pipeline actually performs,
rather than just checking that it runs. It's separate from the unit tests
under `server/src/`, which mock the model out on purpose to test logic in
isolation — this hits the real model.

## What it measures

For each fixture, two different things can go wrong, and the report keeps
them separate:

1. **Extraction accuracy** — did the model correctly read each field off
   the label image, compared against the text actually rendered onto it?
   This is purely "can it read," independent of any comparison logic.
2. **Verdict accuracy** — given what was extracted, did the comparison
   logic (`compareFields`) reach the expected match / needs-review /
   mismatch conclusion? This can fail even when extraction is perfect, if
   the comparison rules themselves are wrong.

## Fixtures

`fixtures/labels/*.jpg` are synthetic label images generated by
`generate_fixtures.py` (Pillow) — plain drawn text on a background, not
photos of any real product. Each one is paired with a known ground-truth
record in `fixtures/fixtures.json`: the exact text drawn onto the image,
an application record to compare it against, and the verdict each field is
expected to produce. The set intentionally covers:

- a perfect match, including a brand-name casing difference that should
  still pass
- a genuine brand mismatch
- an ABV mismatch
- a net-contents unit difference (mL vs L) that should still match
- a Government Warning with altered wording (must fail — no fuzzy
  matching on this field)
- a Government Warning header that isn't all-caps (should be flagged for
  review, not auto-failed)
- a class/type wording variant (should route to review, not be
  auto-decided)
- a rotated/off-angle photo, to check robustness to non-ideal image
  capture

Regenerate the images at any time with:
```bash
python3 generate_fixtures.py
```

## Running it

Requires real model credentials — set `MODEL_API_URL`, `MODEL_API_KEY`,
and `MODEL_NAME` in `server/.env` (this script reads that same file).

```bash
cd eval
npm install
npm run run
```

Output looks like:
```
01_perfect_match
  Brand case differs from the label (Title Case vs ALL CAPS) but should still pass...
  [extract] ✓ brand_name
  [extract] ✓ class_type
  ...
  [verdict] ✓ Brand Name: expected pass, got pass
  ...

============================================================
Extraction accuracy: 38/40 (95.0%)
Verdict accuracy:    39/40 (97.5%)
============================================================
```

## Why this exists

The unit tests prove the comparison logic is correct given a known
extraction result. They don't prove the model reliably produces that
extraction result in the first place — that's a fundamentally different
kind of failure, and the only way to catch it is to run real images
through the real model and check the answers. This harness is small (8
fixtures) on purpose: it's meant as a scaffold to extend, not a finished
benchmark. Natural next additions: a larger, more varied fixture set;
tracking accuracy over time as the prompt or model changes; and fixtures
built from real (synthetic-but-photographic, not hand-drawn) label
photography to better match what agents actually upload.
